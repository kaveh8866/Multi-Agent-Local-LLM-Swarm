Decision: OCI's Ampere **A2** family (VM.Standard.A2.Flex, AmpereOne) in AD-1,

deliberate, documented deviation from the A1 default in terraform.tfvars, not a
silent change: terraform.tfvars is gitignored and holds instance_shape =
"VM.Standard.A2.Flex" for this deployment.

The A1 instances were never created, so nothing was leaked or half-provisioned
at the compute layer; only the network and storage resources below exist.

3. Remote deployment
--------------------
Source transfer: a git archive of tracked files plus the new
docker/compose.oci.yaml was copied over SCP (61 files, 84 KB) and extracted to
~/llm-swarm. The repository was not cloned on the host, so the deployment uses
the exact committed tree rather than whatever GitHub had at that moment.

Secrets: .env was generated from the workstation .env with a fresh 64-hex
orchestrator token, OLLAMA_PORT=11434, OLLAMA_CPUS=8, and the host-side
SWARM_HOST_MODEL_DIR / SWARM_HOST_STATE_DIR pointing at the block volume. It was
transferred out-of-band, installed with mode 600, and never printed. The host
.env is not in Git.

Defect caught during this stage: the overlay first reused SWARM_STATE_DIR for
the host path. That variable is also the worker's *container* path (/app/state),
so the host path leaked into the orchestrator environment and run-record writes
would have gone outside the bind mount. The host variables are now
SWARM_HOST_MODEL_DIR / SWARM_HOST_STATE_DIR, and SWARM_STATE_DIR stays
/app/state.

Failed first attempt (real defect, fixed): the transferred .env carried CRLF
line endings, so `ollama pull` received "qwen2.5:3b-instruct\r" and failed with
"Error: invalid model name". The deploy script now normalises CRLF in .env before
reading it, and the values were re-checked with `cat -A`.

Bind mounts (docker/compose.oci.yaml):
  /mnt/llm-swarm/models  -> /models        (Ollama blobs, 1.8 GB after pull)
  /mnt/llm-swarm/state   -> /app/state     (run records, uid 10001)
  ../configs             -> /app/configs   (read-only)

Proof the weights are on the block volume, not the boot disk:
  docker exec cg-swarm-llm du -sh /models  ->  1.8G
  df -h /mnt/llm-swarm                     ->  1.8G used
  mount unit enabled                       ->  survives reboot

Model pull on the host: "verifying sha256 digest" → "writing manifest" →
"success"; `ollama list` shows qwen2.5:3b-instruct at 1.9 GB.

Stack: `docker compose -f docker/docker-compose.yml -f docker/compose.oci.yaml
up -d --build` → orchestrator ready 6 s after start, /ready body
{"status":"ready","llm":"reachable","model":"qwen2.5:3b-instruct"}.

So all three workflows complete live on the cloud host; one needed a timeout
that matches CPU inference rather than a workstation.

9. Reboot persistence test
--------------------------
The instance was soft-rebooted from the host (uptime reset to "up 0 minutes") to
test persistence rather than assume it.

After the reboot, before any operator action:

  cloud-init status            done
  findmnt /mnt/llm-swarm       /dev/sdb  LABEL=llmswarm  ext4  195.8G
  fstab entry                  LABEL=llmswarm /mnt/llm-swarm ext4 defaults,nofail,noatime 0 2
  df -h /mnt/llm-swarm         1.8G used  (same as before the reboot)
  docker exec ... du -sh /models   1.8G
  docker ps                    cg-swarm-llm Up (healthy)
                               cg-swarm-orchestrator Up (healthy)
  GET /ready                   200 {"llm":"reachable","model":"qwen2.5:3b-instruct"}

So the volume, the 3B weights and both services survive a reboot with no manual
step, which is the persistence guarantee the requirement asks for.

The first completion after the reboot took 26,579 ms for 36 tokens (1.35 tok/s):
the model is not resident in RAM across a reboot, it is loaded from the block
volume on first use. That is cold-start cost, not a throughput regression — the
warm measurements in §4 stand.

**Defect found by this test.** `llm-swarm-mount.service` reported
`failed (status=1)` after the reboot even though storage was healthy. Journal:

  llm-swarm: waiting for the attached block device (attempt 36/36)
  llm-swarm: no data block device found; the volume is probably not attached yet

The unit waits for a device that its own `usable_disk()` deliberately skips when
the disk already has a mount point — and on a normal boot fstab mounts the
volume first. The unit therefore fails *because* nothing is wrong. Fixed in
`terraform/cloud-init.yaml.tftpl` with an early exit when `$MOUNT_POINT` is
already mounted, so the unit reports success on every subsequent boot.

Limitation of this run: the running host still shows the failed unit. Applying
the patched helper to a live host is a root-owned file change, and this agent's
environment declined the privileged command, so it is left to the operator:
re-render `/usr/local/sbin/mount-llm-swarm` from the template, install it as
root (mode 0755), then `systemctl reset-failed llm-swarm-mount` and
`systemctl restart llm-swarm-mount`. New deployments get the fix automatically.
The failure did not affect the mount, the weights or the containers.
