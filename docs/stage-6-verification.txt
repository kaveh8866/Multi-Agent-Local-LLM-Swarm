--------------------------------------------------------------------------------
3. DESTRUCTIVE-ACTION GATE
--------------------------------------------------------------------------------
Teardown is irreversible: it deletes the instance, its boot volume, the 200 GB
data volume with the pulled weights, and the network. Following AGENTS.md §5
the order was plan → approval → destroy → empty state → provider check:

  $ tofu plan -destroy -out=stage6-destroy.tfplan
  Plan: 0 to add, 0 to change, 8 to destroy.

The reviewed plan named exactly the stack from §1:

  module.compute.oci_core_instance.this
  module.network.oci_core_internet_gateway.this
  module.network.oci_core_route_table.public
  module.network.oci_core_security_list.public
  module.network.oci_core_subnet.public
  module.network.oci_core_vcn.this
  module.storage.oci_core_volume.llm
  module.storage.oci_core_volume_attachment.llm

Decision Guard: the operator's Stage 6 request is the approval for this
destructive action, and it was scoped to this project's own compartment and
resource names. No unrelated resource was in the plan and none was touched.
`modules/storage/main.tf` carries no `prevent_destroy` lifecycle, which is why
the data volume was eligible — the module documents that a long-lived swarm
should add it before a real model lands, and this deployment deliberately did
not, because teardown was the requested outcome.

Dependency order was handled by the graph, not by hand: attachment → volume →
instance, then subnet, security list, route table, gateway, VCN. The instance
took the longest because OCI terminates it asynchronously (54 s); the network
teardown was sub-second once the instance was gone, which is the ordering
Stage 5's README warned about.

12. LIMITS OF THIS STAGE
--------------------------------------------------------------------------------
- Billing figures are not read; "zero burn rate" means zero live billable
  resources in the inventory, not a Usage API total.
- The compartment still holds Project 09's running instance and volume. They
  are not this project's and were not touched.
- No volume backup or snapshot was taken; the weights are gone by design.
- The host's `llm-swarm-mount.service` unit failure recorded in Stage 5 §9 was
  never patched on the live host — it disappeared with the instance. The
  template fix remains in `terraform/cloud-init.yaml.tftpl` for future applies,
  still unverified on a booted host.
- The local Compose stack is removed, not rebuilt; `up -d --build` recreates it
  from the same committed files.
- Stage 5's measurements stand as written. Nothing in this stage invalidates
  them: they describe a deployment that existed, not one that exists now.
