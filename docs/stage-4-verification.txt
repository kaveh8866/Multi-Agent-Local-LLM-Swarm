3. Multi-agent collaboration and delegation
-------------------------------------------
Every task config was run concurrently (2 at a time, OLLAMA_NUM_PARALLEL=2),
with the declared step budgets honoured (code_review 8, research_brief 8,
reasoning_chain 10; SWARM_MAX_STEPS=12 is not the binding constraint).

  task                          workflow         status      steps turns  wall
  review-swarm-worker-auth      code_review      completed     5     5   46.5 s
  size-a-swarm-topology         reasoning_chain  completed     6     6  218.2 s
  research-local-llm-serving    research_brief   completed     5     5  166.2 s

  success rate 3/3 = 1.0, agent wall-clock 218.2 s (longest task), 0 errors

An earlier full 3B run on the same configuration also returned 3/3 completed
(wall 220.3 s, peak 655.7% CPU, 4,092.2 MiB), so the 1.0 rate is reproduced,
not a single lucky pass.

Delegation evidence (run records):
  code_review:     planner -> 3x coder (fan-out) -> critic verdict
                   plan = [Correctness of authentication mechanisms,
                           Security vulnerabilities in token handling,
                           Bounded request size limitations]
  research_brief:  planner -> 3x researcher (fan-out) -> critic synthesis
                   plan asks three independent research questions
  reasoning_chain: planner -> 4x researcher (fan-out) -> critic verification
                   plan decomposes the wall-clock question into four steps

All four personas (planner, researcher, coder, critic) were exercised, and the
run records show real delegation rather than one long prompt: the plan stage's
JSON array becomes one turn per planned subtask, and the final stage consumes
the transcript.

Output shape check (closing turn per workflow):
  research brief  -> findings paragraph + explicit open questions + residual
                     risk, no invented measurements ("exact memory footprints
                     were not measured")
  code review     -> blocking findings, non-blocking findings, one-line
                     verdict, residual risk
  reasoning chain -> unsupported steps, contradiction, missing evidence, best
                     supported answer, confidence, residual risk

7. Defects found in the verification tooling itself
---------------------------------------------------
The harness caught two of its own bugs on first use, both fixed before the
certified run:

1. It defaulted to port 11434, which on this workstation is a *native* Ollama
   instance with different models (gemma4:e2b, nomic-embed-text). The result was
   a clean 404 ("model not found") that could easily be misread as a stack
   fault. The harness now derives the URL from OLLAMA_PORT (11435 here) and is
   documented to do so.
2. It overwrote each task's declared max_steps with its --max-steps cap, which
   forced reasoning_chain (declared 10) into budget_exhausted at 5 steps in the
   first 0.5B pass. --max-steps is now an upper bound: effective budget is
   min(declared, cap), matching the orchestrator's own budget rule.

The 0.5B baseline pass (2/3 completed, 1 budget_exhausted, peak 623.7% CPU,
821.5 MiB) is retained as a control; its only failure was the clamp above.

9. Not verified at Stage 4
--------------------------
- No GPU run: the vLLM override was not exercised; all numbers are CPU.
- No cloud run: this is the workstation only (OCI certification is Stage 5).
- Single sample per workflow: three workflows, one run each per pass, so no
  variance or confidence interval is claimed for task success.
- No token accounting for agent runs: the orchestrator does not record usage,
  so tok/s is measured on the direct endpoint, not per agent turn.
- Run records are not persisted by the worker; they exist in the HTTP response
  (captured in the report) and in container logs, not on disk.
- Code-review quality is bounded by the missing file-read tool (see §4).
