--------------------------------------------------------------------------------
1. METHOD
--------------------------------------------------------------------------------
Five independent checks, because each one catches something the others do not:

  A. index scan          — what Git would actually publish
  B. ignore verification — whether the boundary is active for the paths present
  C. content scan        — secret-shaped strings inside tracked files
  D. template review     — whether `.env.example` holds placeholders only
  E. build + runtime     — what leaves the image and what reached the logs

The distinction matters: a file can be ignored yet still tracked from history, and
a path can be tracked while its parent directory looks ignored. Both happened
here (§6) and only the paired checks exposed it.

6. DEFECT FOUND AND FIXED — AN IGNORE RULE THAT HID A TRACKED TEMPLATE
--------------------------------------------------------------------------------
The `.gitignore` model-weights section contained an unanchored directory rule:

  ollama/

Git treats that as "any directory named `ollama`, at any depth", so it also
matched `docker/ollama/` — which holds `Modelfile.swarm`, the optional pinned
sampling parameters and shared system preamble that both the README and
`MANUAL_PREREQS.md` tell an operator to run with `ollama create -f`. The file was
therefore never tracked, while documentation kept pointing at it: a broken
reference that a name-based scan cannot see, because the *directory* is what shows
as ignored.

  before:  git check-ignore -v docker/ollama/Modelfile.swarm
           .gitignore:34:ollama/        docker/ollama/Modelfile.swarm
  after:   git check-ignore -v docker/ollama/Modelfile.swarm
           (no output — not ignored)

Fix: anchor the rule to the checkout root (`/ollama/`), so a root-level Ollama
data directory is still ignored while a source-controlled `docker/ollama/` is not.
`Modelfile.swarm` was reviewed before being added — it contains a `FROM` line,
sampling parameters and a system preamble, no credential — and is now tracked.

This is the only code or configuration change this audit made. Everything else is
read-only inspection.

7. BUILD CONTEXT AND CONTAINER HARDENING
--------------------------------------------------------------------------------
  $ docker compose --env-file .env -f docker/docker-compose.yml config |
      grep -E "cap_drop|read_only|no-new-privileges|pids_limit|max-size|127.0.0.1"
  cap_drop:                (both services)
  - no-new-privileges:true (both services)
  read_only: true          (orchestrator; llama runtime keeps a writable /models)
  pids_limit: 1024 / 256   (runtime / orchestrator)
  max-size: 20m            (both, 3 files)
  host_ip: 127.0.0.1       (both published ports)

The worker image therefore cannot gain capabilities, cannot write outside its
declared mounts, cannot fork-bomb the host and cannot fill the disk with logs. Both
ports are bound to loopback, so even on a host with a permissive firewall the API
is not reachable from the network without a deliberate change.

`docker build` uses `.dockerignore`, not `.gitignore`; the 8 matched rules mean the
image build context excludes `.env`, `runtime/`, `terraform/`, `docs/`, `tests/`,
`*.gguf`, `*.bin`, `*.safetensors`, `*.log` — so a local secret cannot be baked
into a layer even by accident.

9. RESIDUAL RISKS (accepted, documented, not leaks)
--------------------------------------------------------------------------------
  R-1  No TLS on the control plane. The task API is plain HTTP with a bearer
       token; it is loopback-bound and reached through an SSH tunnel. A public
       exposure of port 8090 would be a real finding — the security list and the
       loopback bind are both required to keep this accepted.
  R-2  Shared bearer token, no per-user identity or audit trail. One token grants
       the whole swarm. Rotation means editing `.env` and recreating the worker;
       there is no revocation list.
  R-3  Ollama's own API is unauthenticated by default. `SWARM_LLM_API_KEY` only
       helps behind a proxy; here the port is loopback-bound, so the orchestrator
       is the only client.
  R-4  Run records are not persisted to the state volume, so there is no durable
       audit log of agent turns beyond container logs (which are rotated at
       20 MiB × 3).
  R-5  The vLLM GPU override and the AWS/GCP ports are unexecuted. Unvalidated
       paths can hide defects that a document review cannot find; they are labelled
       as unexecuted everywhere they appear.

No weight, key, state, `.env`, database, log or real OCID is tracked. That is the
zero-leak claim, and it is verified above rather than asserted.
